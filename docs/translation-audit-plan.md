# Translation Audit & Fix Plan — New App Content

**Status:** ready to execute
**Created:** 2026-07-28
**Scope baseline:** commit `3f58613` (*chore: second pass of correcting translation bugs against original intent of english*, 2026-06-25)

---

## 1. Why this exists

In June 2026 two deliberate passes were made over `lib/l10n/*.arb` to align every
translation with the Doxa glossaries and to check each string made sense on its own
terms (commits `b580c54`, `3f58613`). **Everything translated since then has not been
through that process.** Fourteen feature commits have landed since, adding 46 new
English keys and 44 translations per language, plus removing two keys.

The work runs in four phases: parallel assessment, synthesis, parallel implementation,
verification. Assessment agents never write to `.arb` files; implementation agents do,
one file each.

## 2. Source materials (canonical paths)

| What | Where |
|---|---|
| English source strings | `lib/l10n/app_en.arb` |
| Translations under review | `lib/l10n/app_{code}.arb` |
| **The DOXA glossary — SOURCE OF TRUTH** | `https://pray.doxa.life/api/glossary/{lang}`, or `?format=markdown` to read it |
| Prior translation conventions | `docs/translation-guide.md` |

### Authority order — non-negotiable

1. **The glossary for that language** wins. Each term was confirmed by a native
   speaker through a review link, and the response carries the English
   annotations — the definition, an example, why the term matters — so a
   translation can be judged on whether it preserves the *meaning*.
2. **Its `notes` field** carries what no single term holds: register, the verbs
   prayer prompts use, acronym policy, number format, script and name rules.
3. **The `.arb` strings themselves carry no authority.** They are AI-generated and were
   wrong often enough to need two correction passes. Never reason "the other locales all
   say X, so X is right."

### The glossary is the decider — do not escalate

**Every terminology question is resolved from the glossary, not by asking a human.** If a
glossary answers the question, follow it, even where a translation reads oddly to you —
the glossary was reviewed and you were not. If the glossary is *silent* on a term,
resolve it yourself by applying the nearest glossary precedent and the reasoning the
glossary states for comparable terms, then record the decision and the precedent you
applied. Do not defer a translation decision back to the user, and do not leave a string
unresolved pending review. There is no "needs a native speaker" escape hatch in this
audit.

### Do not modify the glossary

The glossary is **read-only for every phase of this work**. It is edited in the
campaigns server's admin by reviewers, and a change there reaches every DOXA
property at once, which is not a side effect an audit of this app should have.
Where the app has legitimately moved past it (see §6.4), the translation must be
made correct on its own merits — the gap is not a reason to edit the glossary,
propose a patch to it, or stall. Record the gap instead; it is a question for
whoever runs the review.

### Hard rules

- **Never edit `lib/l10n/app_localizations*.dart`** — generated by `flutter gen-l10n`.
  Edit the `.arb` source and regenerate.
- Assessment agents (A1–A5, B1, B2) **do not edit any file except their own findings
  file.**
- Implementation agents (D1–D5) edit **exactly one `.arb` file each** and nothing else.
- Do not touch keys outside the §4 scope list, except the specific placeholder-consistency
  keys enumerated in §6.6.
- If English itself is the problem (ambiguous, un-glossaried, inconsistent with the
  glossary), that is a valid finding — file it against `en`. Do not change `app_en.arb`
  during implementation; English changes get raised for a human, since they invalidate
  all five translations.

### 4.3 Sub-vocabularies needing internal consistency

These clusters recur across many strings. Within a language, each cluster must use one
settled rendering throughout — mixing synonyms across a single feature's strings is a
finding even when each string is individually defensible.

- **feedback** — 15 keys. English uses "feedback" as both the noun for the whole feature
  and the thing being sent; languages needing different words for those (e.g.
  *comentarios* / *opinión*, *отзыв* / *обратная связь*, تعليقات / ملاحظات) must choose
  deliberately and consistently. Check `feedbackSubmit` vs `feedbackRateLimited` vs
  `feedbackTypeLabel` in particular.
- **exact alarms** — `allow`, `allowExactAlarms`, `exactAlarmsDisabledStatus`,
  `exactAlarmsPromptBody`. This is Android's own permission name; the translation should
  match the wording of the Android system settings screen in that language so users can
  find it.
- **verification email** — `emailVerified`, `emailUnverified`, `resendVerification`,
  `resendVerification{Sent,Failed,Cooldown,Countdown}`, `newsSignupSuccessBody`. One noun
  for the email, one verb for verifying, consistent everywhere. `emailVerified` /
  `emailUnverified` are adjectival statuses about an *address* — check gender agreement.
- **reminder** — `dismissReminderLabel`, `prayerReminder{Title,Body}`, `exactAlarms*`.
  One noun for "reminder" across all of them.
- **accessibility labels** — 6 keys (`a11y` slot). These are *spoken*, never seen. Judge
  them as speech: no abbreviations, no punctuation artefacts, natural spoken word order,
  consistent with the app's other `*Label` keys.

## 5. Checks and severity

### 5.1 Language reviewer brief (A1–A5)

Each covers **only its own language**. Every key in §4 gets a verdict — including `OK`,
so the synthesis agent can tell "checked and fine" from "not reached".

Apply all seven checks to every in-scope key:

| # | Check | Question |
|---|---|---|
| C1 | **Glossary fidelity** | Does every glossaried term use its glossaried rendering? Cite the glossary section. |
| C2 | **Meaning preserved** | Does the translation say what the English says, including everything the `@key` `description` specifies? No additions, no omissions, no reversed polarity (a dropped negation is a Blocker). |
| C3 | **Standalone sense** | Read only the translation, with no English in view. Is it clear and unambiguous to a user who will never see the English? |
| C4 | **Register & consistency** | Formality (tu/vous, tú/usted, ты/вы, formal vs. informal Arabic), imperative-vs-infinitive button style, and cluster vocabulary (§4.3) consistent with the already-approved strings in the same file. **Read neighbouring approved keys to establish house style before judging the new ones.** |
| C5 | **Grammar & naturalness** | Correct, idiomatic, not translationese. Agreement (gender/number/case), correct spacing and punctuation for the language — French narrow no-break space before `!?:;`, Spanish `¿`/`¡` pairs, Russian `ё` usage matching the file's convention, Arabic diacritics matching the file's convention. |
| C6 | **Placeholders** | `{placeholder}` names intact, spelled identically to English, correctly positioned for the target word order. Plus the guillemet-consistency rule in §6.6. |
| C7 | **Fits the slot** | Length plausible for the `Slot` in §4. Buttons and chips especially. |

Also required:

- **In-language coherence.** Read the strings as a group. Do they sound like one app
  written by one person, or like 44 independent machine translations?
- **Contract with the pre-existing translations.** `dailyPrayerCoverage` replaced
  `prayerCoverage24h`; `engaged` joins the existing `engagementStatus` family;
  `forwardLabel` should pair with however "back"/`continueLabel` is rendered. New strings
  must not contradict old ones.
- **Every finding carries a proposed replacement string, ready to apply.** A finding
  without a concrete replacement is incomplete. Phase 3 applies what you write.

### 5.2 Mechanical agent brief (B1)

Language-agnostic. Some findings are pre-seeded in §6 — **confirm or refute each, then
look for more of the same class.**

1. **Missing keys.** Any key in `app_en.arb` absent from a locale file silently falls back
   to English at runtime. Report the exhaustive list per locale.
2. **ICU placeholder integrity.** Every `{placeholder}` in English must appear, spelled
   identically, in every translation. None dropped, none added, none translated. Affected
   keys: `feedbackSuccessBody`, `newsSignupSuccessBody`, `prayForPeopleGroupLabel`,
   `prayerReminderBody`, `resendVerificationCooldown`, `resendVerificationCountdown`.
3. **Plural / select syntax.** Any ICU `plural`/`select` block must be structurally valid
   and use the categories the target language needs — Russian and Arabic need more than
   English (`one`/`few`/`many`/`other`; Arabic adds `zero`/`two`). Flag any new key that
   should have been a plural but was written flat. Note `fr` `nRemindersSet` currently
   reads `{count}s rappels définis` — verify whether that stray `s` is a defect.
4. **`@key` metadata.** Every key in every locale file must carry its `@key` description
   block, duplicated from the template. Report every missing one — these all get added in
   Phase 3.
5. **Dead keys.** Keys present in a locale file but no longer in `app_en.arb`.
6. **Codebase reachability.** For each new key, confirm it is referenced from `lib/`
   (`grep -rn "l10n\.<key>\|AppLocalizations.of(context)!.<key>" lib/`). An unreferenced
   key is dead weight; a missing one means a hardcoded English string somewhere. Also
   spot-check whether new English UI text was added to `lib/` *without* going through
   `.arb` at all.
7. **Text length.** Flag any translation more than ~1.6× the English character count for
   a constrained slot (`btn`, `lbl`, chips, progress-bar captions). This app has had
   button-bar overflow bugs (`344ff12`, `1d10434`), so this is a real risk.
8. **Non-translatables.** `Doxa` / `DOXA` must appear untranslated and unscripted in every
   language, Arabic and Russian included.

**Not in scope:** alphabetical key ordering — see §6.3.

### 5.3 Vocabulary agent brief (B2)

The glossaries are frozen and read-only. This agent does **not** propose glossary
changes. Its job is to settle the vocabulary the glossaries do not cover, so that
five language reviewers do not each invent a different answer.

1. **Recurring app vocabulary with no glossary entry and no ministry-specific meaning** —
   `feedback`, `exact alarms`, `verification email`, `reminder`, `profile`, `compliment`,
   `notifications`. Determine one canonical rendering per language for each, by applying
   the nearest glossary precedent, the app's existing approved strings, and the platform's
   own terminology (Android settings wording for `exact alarms`). Output a table:
   term × language × canonical rendering × the precedent that justifies it.
2. **Glossary terms used in a new grammatical role.** `engaged` is glossaried as a
   people-group attribute; the app now uses it as a bare standalone chip and a
   screen-reader status. Determine whether each language's glossaried rendering survives
   that use — correct gender/number agreement, no stray article — and if inflection is
   needed, state the inflected form and the glossary basis for it.
3. **`daily prayer coverage`.** The glossary covers "daily prayer" ★ but its coverage
   entry is the superseded 24-hour form. Compose the correct daily rendering per language
   from the glossaried "daily prayer" term plus the glossary's stated constraint on
   "coverage" (uninterrupted prayer through the day, never insurance/legal cover). This is
   a translation decision, not a glossary edit.
4. **`.tsv` ↔ glossary disagreements** for any term the new content touches — report as
   `Note` only, since the glossary is read-only from here.

Its output binds A1–A5's cluster decisions where they conflict; C1 arbitrates.

## 6. Pre-seeded findings and standing decisions

Found while scoping. Agents must still verify, and must look for further instances of the
same class.

### 6.1 Two keys are untranslated in all five locales — **Blocker**

`enableNotificationsButton` ("Enable notifications") and `enableNotificationsPromptBody`
("Enable notifications to also receive updates in push notifications.") exist in
`app_en.arb` but in none of the five locale files. `app_en.arb` has 46 new keys; each
locale has 44. Both currently fall back to English for every non-English user.

**Decision: both must be translated into all five locales.** A1–A5 each supply their
language's translation as a finding; D1–D5 add them, with `@key` metadata.

### 6.2 Missing `@key` metadata blocks — must all exist

19 of the 44 new keys arrived in the locale files without the duplicated `@key`
description block that the rest of each file carries: `dismissReminderLabel`, `engaged`,
all 15 `feedback*` keys, `prayerReminderBody`, `prayerReminderTitle`.

**Decision: every key in every locale file must have its `@key` block.** B1 produces the
exhaustive list; D1–D5 add the missing blocks, copying the description from
`app_en.arb`. Together with §6.1 that is 21 blocks per locale, plus any further ones B1
turns up.

### 6.3 Alphabetical key ordering — no action

Locale files were fully sorted at `3f58613`; the new keys were appended or inserted out of
order (first breaks: `engagementStatus` → `engaged`, then the `newsSignupSuccess*` /
`accountSectionTitle` run). `app_en.arb` is not sorted and never was.

**Decision: leave it.** Keys sit in alphabetical position. D1–D5 should insert new keys at their
alphabetical position where that is obvious, but must not perform a whole-file re-sort —
it would bury the real changes in diff noise.

### 6.4 "24-hour" → "Daily" prayer coverage — intentional, glossary stays frozen

Commit `2e964bc` renamed the English from "24-hour prayer coverage" to "Daily prayer
coverage" and replaced key `prayerCoverage24h` with `dailyPrayerCoverage`. **This is a
deliberate change: the ministry goal itself changed from 24-hour coverage to daily
prayer.** `glossary.md` §3 and all five `.tsv` files still carry only the superseded
24-hour form (e.g. `fr.tsv`: `24-hour prayer coverage` → `couverture de prière 24h/24`).

**Decision: the translations must be correct regardless of the glossaries' silence, and
the glossaries are not to be changed.** Build the rendering from the glossaried "daily
prayer" ★ term plus the glossary's constraint on "coverage" — uninterrupted prayer
through the day, never insurance or legal cover. B2 sets the canonical per-language form;
A1–A5 assess their language against it. Do not propose a glossary patch.

### 6.5 `engaged` renderings diverge in strategy — **needs glossary check per language**

`fr` "Engagé", `pt` "Engajado", `ru` "Вовлечён", `es` "Comprometido", `ar` "مُنخرَط".
`fr.tsv` pairs `engaged` → `engagé`, so French matches its glossary. **Unverified for the
other four.** `es` "Comprometido" (*committed*) is the likeliest defect, since the English
glossary explicitly warns against rendering the missions term as generic involvement or
commitment. A2–A5 check against their own glossary and correct to whatever it says; C1
compares strategies across all five.

### 6.6 Placeholder guillemets — consistency, not correctness

Guillemets around a placeholder are **typography only**. `{peopleGroup}` is the ICU token;
surrounding characters are literal text, so a bare placeholder substitutes correctly —
`app_en.arb` uses none and works. Nothing here is functionally broken.

The established convention in the approved strings is guillemets on **name-like**
placeholders (`{name}`, `{currentName}`, `{newName}`, `{peopleGroup}`) and never on
numeric or technical ones (`{count}`, `{time}`, `{weekday}`, `{version}`, `{seconds}`,
`{email}`). Current state:

| Locale | Name placeholders | Gaps |
|---|---|---|
| `ar` | guillemets throughout | new keys already consistent |
| `ru` | guillemets throughout | new keys already consistent |
| `fr` | guillemets with spaces, `« {name} »` | new `prayForPeopleGroupLabel`, `prayerReminderBody` are bare |
| `es` | mixed | `scanToPray`, `switchPeopleGroupConfirm` bare; both new keys bare |
| `pt` | none anywhere | all name placeholders bare |

**Decision: each language applies its own guillemet convention uniformly to every
name-like placeholder in its file — new keys and the approved keys that currently break
it.** Numeric and technical placeholders stay bare in every language. Where a language
has no convention today (`pt`), the reviewer picks the one standard for that language and
applies it throughout. French keeps its narrow no-break spacing inside the guillemets.

This is the one place implementation may touch approved strings. The eligible keys are
exactly: `peopleGroupIntroTitle`, `scanToPray`, `shareMessage`,
`switchPeopleGroupConfirm`, `wizardConfirmPeopleGroupTitle`, `prayForPeopleGroupLabel`,
`prayerReminderBody`. Severity **Minor** — never let it displace a Blocker.

### 6.7 `partial` — adverb vs adjective, unconfirmed

`ru` "Частично" is an adverb (*partially*); the Romance locales use adjectives
("Parcial", "Parcial", "Partiel"). Either can be right depending on what the screen reader
utters it alongside. A5 verifies against the actual announcement context in `lib/`.

### 6.8 `forwardLabel` renders as "next", unconfirmed

`ar` "التالي" and arguably `pt` "Avançar" say *next*, not *forward*. The `@key`
description says it labels a forward *navigation arrow*. Check against how the paired
back/continue control is rendered in the same file (`continueLabel` exists). **Minor**.

## 8. Phase 2 — synthesis (C1)

Runs only after all seven Phase 1 files exist.

1. Read all seven findings files.
2. **Cross-language consistency pass.** For each glossary-sensitive key in §4.1, lay the
   five translations side by side. If one language diverges in *strategy* — e.g. four
   render `engaged` with the glossaried missions term and one uses a general-purpose word —
   that is a finding even if no single reviewer flagged it.
3. **Arbitrate conflicts** between a language reviewer's cluster choice and B2's canonical
   rendering. B2's table wins unless the reviewer cited a specific glossary section that
   overrides it — the glossary always outranks a cross-language consistency preference.
4. Dedupe: one issue reported by five reviewers becomes one finding with five instances.
5. Rank by §5.5 severity, then by user-visibility.
6. Write `docs/translation-audit/REPORT.md`:
   - **Blockers** — wrong meaning, untranslated strings, broken placeholders.
   - **Terminology corrections** — glossary mismatches.
   - **Polish** — register, naturalness, length, placeholder typography (§6.6).
   - **Mechanical** — missing keys, missing `@key` blocks, per §6.1 and §6.2.
   - **Raised for a human** — English-source problems only. No translation decision may
     land here.
   - **Coverage table** — key × language × verdict, so gaps in the audit itself are visible.
7. **Per-language change sets.** The critical output for Phase 3: for each language, a
   flat ordered list of `key → exact final string`, covering every accepted change plus
   the two new keys. D-agents apply these verbatim, so any ambiguity left here becomes a
   defect there.
8. State plainly what the audit could not determine.

**Definition of done:** seven findings files with complete verdict tables (46 keys × 5
languages accounted for); `REPORT.md` with all six sections plus five per-language change
sets; every Blocker carrying a final string for every affected language; no `.arb` or
generated Dart file modified.

## 9. Phase 3 — parallel implementation (D1–D5)

Five agents, launched **in parallel**, one per language. The parallelism is safe because
each agent is the **sole writer of exactly one file** — there are no shared writes.

| Agent | Owns, exclusively |
|---|---|
| D1 `apply-ar` | `lib/l10n/app_ar.arb` |
| D2 `apply-es` | `lib/l10n/app_es.arb` |
| D3 `apply-fr` | `lib/l10n/app_fr.arb` |
| D4 `apply-pt` | `lib/l10n/app_pt.arb` |
| D5 `apply-ru` | `lib/l10n/app_ru.arb` |

### 9.1 Prompt template for D1–D5

> You are applying the audited translation fixes for **{LANGUAGE}** to
> `lib/l10n/app_{SHORT}.arb`. You are the only agent writing to that file. Do not read
> from or write to any other `.arb` file.
>
> Read:
> 1. `docs/translation-audit/REPORT.md` — authoritative. Its **{LANGUAGE} change set**
>    (§8.7) is your work list: `key → exact final string`.
> 2. `docs/translation-audit/findings-{SHORT}.md` — the reasoning behind each change, for
>    when the report is terse.
> 3. `docs/translation-audit/findings-mechanical.md` — the rows for {LANGUAGE}.
> 4. `docs/translation-audit/findings-vocabulary.md` — canonical renderings.
> 5. `https://pray.doxa.life/api/glossary/{CODE}` — if any change looks
>    wrong to you, check it here. The glossary decides, and is read-only from here.
>
> Apply, to `lib/l10n/app_{SHORT}.arb` only:
> - Every change in your language's change set, using the report's exact strings.
> - The two missing keys `enableNotificationsButton` and `enableNotificationsPromptBody`,
>   with their translations from the report (§6.1).
> - Every missing `@key` description block, copying the description text verbatim from
>   `app_en.arb` (§6.2).
> - Your language's placeholder-guillemet convention, applied uniformly across the seven
>   eligible keys listed in §6.6 — and only those seven.
>
> Do not:
> - Touch any file other than `lib/l10n/app_{SHORT}.arb` and your own report file.
> - Edit `app_en.arb` or any `app_localizations*.dart` — the Dart is generated.
> - Re-sort the file. Insert new keys at their alphabetical position where obvious;
>   Leave the rest of the ordering alone (§6.3).
> - Change any string not named in the report.
> - Substitute your own wording for the report's. If a report string is genuinely
>   unusable, apply nothing for that key and record why in your output file.
>
> Before finishing, verify your file is valid JSON, that every `{placeholder}` matches
> `app_en.arb` exactly, and that your key set now equals `app_en.arb`'s.
>
> Write `docs/translation-audit/applied-{SHORT}.md`: every key changed with before/after,
> every key skipped with the reason, and your JSON/placeholder/key-parity check results.

### 9.2 Definition of done

- All five `.arb` files updated; each is valid JSON.
- All five locale key sets equal `app_en.arb`'s — no missing keys, no dead keys.
- Every key in every locale file has its `@key` block.
- Five `applied-{code}.md` files, every change set item either applied or explained.
- `app_en.arb` and all `app_localizations*.dart` untouched.

## 10. Phase 4 — verification (sequential, orchestrator)

Runs once, after all five D-agents finish. Not parallel — `flutter gen-l10n` writes shared
generated files, so it must not race.

```bash
# 1. key-set parity, JSON validity, placeholder parity, @key coverage
python3 tool/check_arb.py      # write this if it does not exist

# 2. regenerate the localizations — never hand-edit the output
flutter gen-l10n

# 3. static analysis
flutter analyze

# 4. confirm only the intended files moved
git status --short
git diff --stat lib/l10n/
```

Expected: `lib/l10n/app_{ar,es,fr,pt,ru}.arb` modified, `app_localizations_*.dart`
regenerated, `app_en.arb` untouched.

Then **hand off for human audit of the findings and the applied diffs.** Anything that
comes out of that review is fixed in a follow-up pass, not by re-running this plan.
